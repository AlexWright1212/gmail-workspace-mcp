# ADR 009 — Attachment Outbox for Files That Live on the Client Machine

**Last edited:** 2026-09-19 (Amendment: the same drop box serves `upload_drive_file`, plan 002 Phase 4)
**Status:** Accepted
**Origin:** ad hoc

---

## Context

While discussing `docs/adr/008-accept-unconfined-attachment-path-risk.md`, the
owner asked a workflow question about a real scenario: "grab the PDF I just
downloaded and email it to my professor." That surfaced a gap distinct from
008's confinement question.

`readAttachment()` (`src/compose.ts`) runs inside the server process — the
VPS — not on whichever machine the calling MCP client happens to be on. A
path like `~/Downloads/assignment.pdf` is meaningless there: the VPS has no
such user or home directory. Before this change, attaching a file that lives
only on the owner's laptop was not silently wrong (the existing `ENOENT`
error in `readAttachment()` already fails loudly — no half-built message, no
wrong file sent) but it was simply impossible. There was no path from "the
file is on my laptop" to "it's attached to a draft."

## Options Considered

**Inline the file's bytes (base64) directly in the tool call.** No new
infrastructure — add a `content` field alongside `path`. Rejected as the
general solution: MCP tool-call arguments are typically generated by the
model itself as literal output tokens, so this means the model emitting the
entire base64-encoded file as output. Workable for a short text file,
impractical for anything in the hundreds of KB to MB range (a typical PDF) —
slow, expensive, and liable to hit output limits. Not pursued as a dedicated
mechanism; a caller is still free to pass small inline content if a future
need justifies adding the field.

**Run the server in `stdio` mode locally when a local attachment is needed,
instead of over the deployed SSE/Tailscale connection.** The code already
supports this transport (`connectLocal()`), and it would make local paths
resolve correctly with zero new server-side logic. Rejected: it means running
two live configurations of this server — VPS-always-on for normal use,
local-on-demand for attachments — which cuts against the project's existing
"one source of truth for where this runs" discipline, and would require
Gmail credentials to be reachable locally too.

**A shared drop-box directory on the VPS, populated by the calling agent's
own existing SSH access.** The agent already holds SSH/deploy credentials for
the VPS in the owner's actual usage pattern (the same fact `docs/adr/
008-accept-unconfined-attachment-path-risk.md` leans on) — no MCP tool call
is needed to move the bytes over; a plain `scp` does it, no size ceiling. The
Gmail MCP tool then only ever needs to accept a path that's already local to
the machine it runs on, which is the case `readAttachment()` already handled
correctly. Chosen.

## Decision

**A dedicated outbox directory on the VPS, `/root/.gmail-multi-mcp/outbox`
(overridable via `MCP_OUTBOX_DIR`, used by tests to point at a temp dir
instead of root's real path). Files read from it are deleted once their
bytes are captured; everything else is unaffected.**

Workflow: copy the file to the VPS with `scp` (same key already used for
deploys) → reference the resulting VPS path in `attachments[].path` → the
existing `create_draft`/`send_message` tools work unchanged.

Implementation, `src/compose.ts`:
- `resolveOutboxDir()` — env override or the fixed default.
- `cleanupIfInOutbox(filePath)` — resolves both the outbox dir and the
  attachment path via `fs.realpath` (so a symlink inside the outbox pointing
  elsewhere is correctly *not* treated as an outbox file — neither the link
  nor its target gets deleted) and unlinks only when the attachment's real
  path is actually inside the outbox. Best-effort: a missing outbox dir or a
  failed `unlink` never fails the compose call — by the time cleanup runs,
  the bytes are already captured into the return value, so a cleanup miss is
  a stale file, not a broken send/draft.
- Called from `readAttachment()` immediately after a successful read, for
  every attachment, on both `create_draft` and `send_message` (they share
  the one `buildMimeMessage()` path).

Cleanup is delete-on-successful-read only — no nightly sweep, no
retry-if-send-fails cache. Deliberate: the files involved are small
(kilobytes to low single-digit megabytes) and the owner's usage is
occasional, so a stray orphaned file from a failed multi-attachment build is
a low-stakes, self-correcting nuisance, not worth a second cleanup mechanism.

Tool schema (`src/index.ts`): `attachments[].path` on both `create_draft` and
`send_message` now explains the VPS-vs-client-machine distinction and the
outbox convention directly in its description — the same progressive-
disclosure pattern already used for `ATTACHMENT_READ_TOOL` (`get_email_thread`'s
description dynamically names the tool that reads attachment content). Any
MCP client gets this the moment it lists tools; no client-specific config
file (`AGENTS.md`, etc.) is needed, and it costs nothing in sessions that
never touch this server.

`scripts/deploy.sh` now creates and locks down the outbox directory
(`mkdir -p` + `chmod 700`) on every deploy — idempotent, so it self-heals if
the directory is ever deleted by hand.

New tool, `tools/fetch-attachment.mjs`: fetches one attachment's exact bytes
via `messages.attachments.get`, decoded straight to a `Buffer`. Built because
`tools/raw-mime.mjs`'s `.toString('utf8')` decode step is lossy for binary
attachment bytes — it was built for reading headers and text bodies, not
byte-exact reproduction — so it cannot verify attachment fidelity for
anything but plain text. This is what makes the human-verification checksum
comparison for this feature (`docs/human-verification.md`, step 7b)
trustworthy rather than "looked right in Gmail."

## What's Now Known

- 5 new unit tests in `test/compose.test.mjs` (230/230 total, passing):
  byte-correct embedding outside any outbox, delete-on-success inside the
  outbox, non-outbox files left alone even with an outbox configured, a
  symlink inside the outbox pointing outside it is not treated as an outbox
  file (neither the link nor its target is touched), and a missing/
  unconfigured outbox dir doesn't break a normal attach.
- Deployed via `scripts/deploy.sh`: outbox directory created and verified
  (`mkdir -p` + `chmod 700`, confirmed via the deploy script's own command
  chaining under `set -euo pipefail`), module graph verified, `pm2` restarted
  and confirmed `status=online`.
- **Not yet run:** the real end-to-end loop (real Gmail draft, real
  delete-after-attach on a real VPS file) — that's
  `docs/human-verification.md` step 7b, and per this project's standing
  verification discipline, it requires the owner, not an agent.

## Consequences

- MCP clients must reconnect to pick up the changed `attachments[].path`
  description — the tool list is unchanged, but its schema text is, and a
  stale cached tool list won't show the new guidance.
- This does not change `docs/adr/008-accept-unconfined-attachment-path-risk.md`'s
  decision. `readAttachment()` is still unconfined in general; the outbox is
  an additional, specific, populated case of that same unconfined behavior,
  not a confinement mechanism. A path outside the outbox still works exactly
  as it did before this ADR.
- While touching `docs/machine-setup.md` and `README.md` for the outbox
  workflow, both were found to still describe the pre-ADR-007 plain-HTTP
  public endpoint (`http://203.0.113.10:3000/sse`) as current — stale since
  that ADR, unrelated to this change, but actively misleading for anyone
  setting up a new client. Corrected in the same pass: both now point at
  `http://100.64.0.10:3000/sse` and note the Tailscale-join prerequisite.
  `docs/tickets/002-http-not-https.md` and ADR 007 itself were left alone —
  their old-IP references are historical (describing the pre-fix state) and
  correctly worded in the past tense.

## Amendment (2026-09-19, plan 002 Phase 4)

`upload_drive_file` reuses this drop box, under a stricter rule than mail
attachments: the path **must** resolve inside the outbox (`assertInsideOutbox()`
in `src/outbox.ts`, realpath on both sides so a symlink cannot point elsewhere)
or the call is refused before any Google call, and the file is deleted after a
successful upload. Mail attachments keep ADR 008's accepted risk — a path
anywhere on the VPS is readable and left in place. The difference is
deliberate: an attachment still passes through MIME composition and the send
allowlist, so the outbox is a convenience on a gated path; a Drive upload has
no equivalent gate, so the outbox is its only path control. Both callers share
one resolver so the directory and the containment rule cannot drift apart.
Verified live by the harness from both accounts (upload from the outbox
succeeds and the file is gone from disk; a path outside it is refused and
nothing appears in Drive).
